CrazyFlie-2.1 · l2f · branch feat/moo · plan of code changes · final draft for review

PyTorch training and reward changes

The planned code changes, in steps 0 to 6, each change with its check. Code that needs no measurements comes first, the survey on the drone sits in the middle, then calibration and validation, then flights. The simulator moves to simulated sensors running through the firmware's own Kalman filter. Decisions made, work put off, and open questions are at the end.

Status

  • Nothing in this plan is implemented, except the crash-penalty draft (B3: L2F_CRASH_PENALTY in reward_functions/brushless.h, CRASH_PENALTY= in train_mission.sh; default 0, not yet compiled). Pushed to feat/moo on 2026-11-21 with it: the stale ground-effect comment removed from rl_trigger.py, the formula rule in AGENTS.md, the asd-ste100 skill with its Foundation mode, and this plan as l2f/pytorch_training_plan.html.
  • Rule for every change: the new behaviour sits behind an option, so the old recipe can still be reproduced. A change is kept only if it beats the baseline on 3 seeds (late-checkpoint medians, moo_summary.py checkpoints) without raising the crash rate, and then in flight.
  • Every sensor number is a parameter in one file, config/sensors.yaml, with a published prior and a measured value. Neither is trusted on its own: the survey (Step 4) flags any parameter where the two disagree by more than 2×, and each flag needs an explanation before its value is used.

Simulator architecture decided

Keep the Flow deck (it gives a better state), and simulate what the drone's estimator actually does with it: simulated sensor readings go through the firmware's own Kalman filter, and the policy sees that filter's output.

            (physics)     (sensors.yaml)    (kalman_core, mm_*)        (as rl_tools_controller.c)

old path    true state + noise + delay + jumps ──────────────────────────────────────────► actor
(kept)      baseline for the PyTorch match (A5), old recipes, and the interim per-axis noise (C5)
  • The deck's effects are structural. Below 10 cm the firmware's flow model uses 0.1 m instead of the true height; the range sensor is only accurate from 4 cm; the flow is de-rotated with the gyro; the range reading is corrected for tilt and ignored above about 84°; Lighthouse and the range sensor are blended. Running the same estimator code gets all of these without a special rule for each.
  • The parameters are physical. Noise densities, minimum ranges, fields of view and rates have published values and can be measured one by one.
  • The errors get the right shape. Lighthouse V2 jitter is 0.7 mm, but its accuracy is about 1 cm with flight outliers up to 5 cm [6]: mostly slow error. Slow errors, the filter's lag and correlation, and jumps from base-station drop-outs come from the filter and the base-station geometry.
  • Firmware changes can be tested in simulation before they are flashed, because it is the same code (E4).

C3, D1 Landing the same way as the flight script, in training and evaluation decidedC++ and Python

  1. The target descends at v_d (0.1–0.25 m/s) to 2 cm below the floor.
  2. The motors cut when the target is in its last 10 cm and the estimated height is below h_cut (Q2), or 2 s after the target reaches the floor.
  3. The drone falls; the episode ends as a landing. Reward on that step: c / (1 − γ) = 200 with the bonus, 0 without.
v_touch = √(v_d² + 2·g·h_cut) v_d = 0.1 m/s: 2 cm → 0.63 m/s, 3 cm → 0.77 m/s, 6 cm (flight today) → 1.09 m/s

Applies to the training landing episodes and to evaluate_robustness's mission test. The values (below, the 10 cm window, h_cut, the timeout, v_d) are defined once in config/landing.yaml, read by rl_trigger.py (D1: its --cut-height default) and by training. The cut uses the estimated height, so its realism improves once the new path is in use (Steps 2 and 5). The lower cut height is flown only after Step 5 decides it.

B1 Zig-zag penalty replaces action rate decidedC++

today: C_rate = Σ_i (a_i,t − a_i,t−1)² weight 1 new: C_zigzag = Σ_i (a_i,t − 2·a_i,t−1 + a_i,t−2)² weight 0.25 (start)

At 50 Hz chatter, 0.25 · 16 = 1 · 4, so chatter costs the same as today; at 2 Hz manoeuvres about 60× less. The state keeps at least 2 past actions; the actor's input does not change. The C++ default stays rate so old recipes reproduce.

D2 Gyro-saturation count in flight logs decidedrl_trigger.py

The real-flight counterpart of C1 and C2: it shows whether a flight ever reached the gyro's range, where the reading stops being correct. rl_trigger.py does not log the gyro today, so this adds a log block with gyro.x, gyro.y, gyro.z at 10 ms (100 Hz; saturation events last tens of milliseconds, and the show run's lasted 5 samples at 10 ms), written to the flight CSV. The flight summary reports:

saturated sample: max(|gyro.x|, |gyro.y|, |gyro.z|) ≥ 1990°/s (just under the ±2000°/s range; readings can exceed 2000 slightly after bias removal) summary: count of saturated samples · longest run of consecutive ones (ms) · peak per axis

Once the reading is at the range, the log cannot show how fast the drone really turned, only that it reached the range and for how long. The longest run bounds how long the estimator integrated a wrong rate.

Check
on a flip.py log, the count matches the samples at the range found by reading the CSV directly

E2 Sensor models C++

gyro for the filter: 10 ms average of (ω + b_g + n_g + n_vib(rpm)), clipped at ±34.9 rad/s for the actor: LPF₈₀(…) latest sample, as rl_tools_controller.c reads sensors->gyro accel 10 ms average of Rᵀ(a − g) + b_a + n_a + n_vib(rpm) range d = (z_sensor − z_floor) / cos α + e(d) + n_r, e, n_r from the spacer test ~40 Hz d < 0.04 m: the measured below-minimum behaviour (§7.3: not accurate) flow n_x = (Δt · 35 / 0.717) · (v_x · cos θ / h_cam − ω_y) + n_f, quantized 100 Hz out of specification when h_cam < 0.08 m or |v / h| > 7.4 rad/s, or on low quality (squal): behaviour from the slide test (the sensor may read wrongly, not only stop) LH sweep angles from the base-station geometry (+ calibration error δ_geo), σ_angle, drop-outs as a random process with the logged rate and duration

The filter only ever sees the 10 ms IMU averages, so the model produces those directly; their noise is the measured noise of the average (white electronic noise shrinks by √10 over 10 samples, vibration tones may not). Every constant comes from config/sensors.yaml and can be randomized per episode within its randomize range. n_vib, measured in the hover mode against motor RPM, is what makes the in-flight gyro noise 0.069 rad/s.

D3 Sensor survey new scriptdecided

A new script, noise_survey.py (logging through run_log). Every survey flight is flown in the learned-flight configuration, with only the Lighthouse and Flow decks and no AI deck, so the measured vibration matches the real flights (a heavier drone hovers at higher motor RPM and vibrates differently). It records the raw sensor readings that go into the estimator and the estimate itself, so it calibrates the new path (Step 2) and the old one (C5):

  • raw: gyro.*, acc.*, range.zrange, motion.deltaX, motion.deltaY, motion.squal, motor RPM (motor.m*_rpm), and the Lighthouse angles (lighthouse log group; which angles it carries for Lighthouse V2 is to be checked)
  • estimate: stateEstimate.*

cflib's logging runs at most at 100 Hz per log block (the period is set in 10 ms units, cflib/crazyflie/log.py), so this capture is 100 Hz, split over several log blocks. It is enough for every statistic below and for the tolerance replay in E1. Exact replay needs D4. Five modes:

  1. still: on the floor, motors off, at several spots including the take-off and landing spot. Per spot: σ, mean, and the height offset from the take-off spot.
  2. heights: resting on spacers of known height (0, 1, 2, 3, 5, 10 cm). Gives the range sensor's bias and σ against a known distance, including below its 4 cm minimum, and its distance from the floor when landed.
  3. hover: stock-PID hovers at several heights (for example 0.3, 0.6, 1.0, 1.5 m). Noise in flight = x − lowpass(x) with a 5 Hz centred low-pass; gyro and accelerometer spectra against motor RPM (the vibration model).
  4. slide: on a spacer, pushed along a timed straight 1 m track. Ratio of estimated to true speed (distance / time) at each spacer height, with flow on and off.
  5. logs: reads existing rl_trigger flight logs (on the flying machine) for Lighthouse drop-outs and jumps: rate, size, duration, direction.
σ_q,i = std(x_noise) per quantity q, axis i, spot / height / hover r₁ = corr(x_noise,t , x_noise,t−1) lag-1 autocorrelation (≈ 0: white) g(h) = mean(v_estimated) / (distance / time)

It writes the measured fields of config/sensors.yaml, and l2f/sim/noise_measured.json (estimate-level statistics for the old path), and flags every parameter where measurement and prior differ by more than 2×.

D4 Estimator-input streamer through the AI deck optionalfirmware apphost script

Built only if E1's check 2 (the tolerance replay of the 100 Hz survey logs) shows differences that cannot be explained (Q12). It gives exact replay without an SD card deck. The AI deck is needed for nothing else: not for the survey, not for training, not for learned flights. A small firmware app sends what the estimator consumes, timestamped, as CPX packets to the AI deck, whose ESP32 forwards them over WiFi to a host script:

  • the 10 ms gyro and accelerometer averages that the prediction step uses (axis3fSubSamplerFinalize → kalmanCorePredict, estimator_kalman.c), and the "flying" flag it is called with
  • every measurement event the firmware already defines for SD-card logging: estTOF, estFlow, estSweepAngle (estimator.c), in the format bindings/util/sd_card_file_runner.py reads
  • the estimate after each prediction
data rate ≈ IMU averages 100 Hz · 28 B + ToF 40 Hz · 12 B + flow 100 Hz · 12 B + sweeps ≈ 400 /s · 12 B ≈ 9 kB/s link: CPX UART to the AI deck at 576,000 baud (Kconfig default) ≈ 57 kB/s

The AI deck adds mass, so it is fitted only on these replay flights, never on survey or learned flights. The mass of each replay flight is recorded for the replay check (E5).
